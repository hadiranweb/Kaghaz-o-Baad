# گزارش ممیزی احراز هویت با تلفن و ایمیل

**وضعیت:** اصلاحات کدنویسی‌شده و آمادهٔ بررسی در branch فعلی؛ هنوز deploy production و تست پیامک واقعی انجام نشده است.

## جمع‌بندی اجرایی

فرایند ارسال OTP تلفنی از نظر قرارداد اصلی SMS.ir درست طراحی شده است: backend به endpoint `POST https://api.sms.ir/v1/send/verify`، هدر `X-API-KEY` و payload شامل `mobile`، `templateId` و `parameters` متصل می‌شود. مستندات SMS.ir تصریح می‌کند که نام پارامتر باید بدون علامت‌های `#` و مطابق کلید تعریف‌شده در قالب ارسال شود؛ بنابراین برای قالب اعلام‌شدهٔ `#CODE#` مقدار `SMSIR_CODE_PARAMETER` باید دقیقاً `CODE` باشد، نه `Code`.[1]

در نسخهٔ اصلاح‌شده، کد OTP هرگز به‌صورت خام در دیتابیس ذخیره نمی‌شود و فقط SHA-256 آن ذخیره می‌شود. کد پس از مصرف به‌عنوان consumed علامت‌گذاری می‌شود، مدت اعتبار پیش‌فرض ۱۲۰ ثانیه است، حداکثر تلاش پیش‌فرض ۵ بار است، و ارسال مجدد برای هر شماره به یک درخواست در ۶۰ ثانیه محدود شده است. موفقیت در واردکردن کد، از این پس `profiles.phone_verified_at` را مقداردهی می‌کند؛ بنابراین ورود تلفنی واقعاً یک عامل تأییدشده تولید می‌کند.

## نتیجهٔ ممیزی رفتار فعلی

| مسیر | رفتار فعلی | نتیجهٔ verification |
|---|---|---|
| ورود با تلفن | ارسال OTP، اعتبارسنجی hash، انقضا و rate limit | پس از کد صحیح، `phone_verified_at` ثبت می‌شود و عامل تلفن تأییدشده است. |
| ورود با ایمیل و رمز | بررسی رمز و ساخت session | اگر `email_verified_at` قبلاً مقدار داشته باشد عامل ایمیل تأییدشده است؛ در غیر این صورت صرفاً احراز رمز انجام شده و ایمیل تأییدشده محسوب نمی‌شود. |
| ثبت‌نام با ایمیل و رمز | کاربر و session بلافاصله ساخته می‌شود | **شکاف باقی‌مانده:** چون email verification flow وجود ندارد، این مسیر می‌تواند حسابی بدون عامل تأییدشده بسازد. |
| OAuth با Google/GitHub | برای provider، ایمیل دریافتی در صورت وجود trusted و `email_verified_at` ثبت می‌شود | در صورت بازگشت ایمیل provider، عامل ایمیل تأییدشده است. اعتبار این رفتار به قرارداد provider و پاسخ واقعی آن وابسته است. |
| افزودن عامل دوم از داشبورد | endpoint جدید و کارت UI اضافه شده است | کاربر session فعال، شماره را وارد می‌کند، OTP می‌گیرد و پس از کد صحیح شماره به حساب متصل و تأیید می‌شود. |

## تغییرات اعمال‌شده

Migration شمارهٔ `016_verified_auth_factors.sql` ستون `profiles.phone_verified_at` را اضافه می‌کند و purpose کدهای OTP را از فقط `login` به `login` و `phone_verification` گسترش می‌دهد. همچنین indexهای لازم برای lookup و گزارش‌گیری اضافه شده‌اند.

در backend، موفقیت OTP تلفنی اکنون عامل تلفن را ثبت می‌کند. دو endpoint جدید برای تکمیل عامل دوم اضافه شده‌اند:

```http
POST /api/v1/auth/phone/verify-factor/send-code
Authorization: Bearer <session-token>
Content-Type: application/json

{"phone":"09121234567"}
```

```http
POST /api/v1/auth/phone/verify-factor
Authorization: Bearer <session-token>
Content-Type: application/json

{"phone":"09121234567","code":"123456"}
```

پاسخ `GET /api/v1/auth/me` اکنون شامل `email_verified`، `phone`، `phone_verified` و `has_verified_factor` است. در frontend نیز typeها، client functionها و view «امنیت و عوامل تأیید» به Dashboard افزوده شده‌اند.

## قرارداد OTP و تایمرها

| کنترل | مقدار فعلی | توضیح |
|---|---:|---|
| TTL کد | ۱۲۰ ثانیه | قابل تنظیم با `OTP_TTL_SECONDS` و حداکثر ۹۰۰ ثانیه. |
| تلاش تأیید | ۵ بار | با `OTP_MAX_ATTEMPTS` کنترل می‌شود؛ شمارنده قبل از مقایسه افزایش می‌یابد. |
| ارسال مجدد برای هر شماره | ۱ بار در ۶۰ ثانیه | پاسخ HTTP 429 باید `Retry-After` و `retry_after_seconds` داشته باشد. |
| محدودیت IP ارسال | ۵ بار در ۱۰ دقیقه | برای کاهش SMS flooding. |
| محدودیت تأیید | ۱۰ بار در ۱۰ دقیقه | برای هر شماره، IP و مسیر factor. |
| مصرف دوبارهٔ کد | غیرممکن | پس از موفقیت یا خطای provider، رکورد consumed می‌شود. |
| نشت کد | جلوگیری‌شده | کد خام در log و database نوشته نمی‌شود؛ `messageId` فقط برای tracing ذخیره می‌شود. |

تایمر frontend صرفاً راهنمای تجربهٔ کاربر است و مرجع امنیتی نیست؛ backend باید TTL و rate limit را مستقل enforce کند. با هر ارسال موفق، UI وارد مرحلهٔ code می‌شود و دکمهٔ ارسال مجدد تا ۶۰ ثانیه غیرفعال می‌ماند. اگر کد منقضی شود یا تمام تلاش‌ها مصرف شود، کاربر باید از مسیر ارسال مجدد اقدام کند.

## نکتهٔ حساس دربارهٔ قالب `#CODE#`

در پنل SMS.ir باید کلید پارامتر دقیقاً بررسی شود. بر اساس متن قالب اعلام‌شده، مقدار اجرایی پیشنهادی این است:

```env
SMSIR_TEMPLATE_ID=776448
SMSIR_CODE_PARAMETER=CODE
```

اگر پنل SMS.ir کلید را با حروف کوچک/بزرگ دیگری ثبت کرده باشد، مقدار environment باید همان کلید واقعی پنل باشد. اضافه‌کردن `#` به مقدار environment اشتباه است؛ backend باید نام پارامتر را بدون `#` ارسال کند.[1]

## شکاف‌های باقیمانده و تصمیم لازم

قانون «حداقل یک عامل تأییدشده» اکنون برای وضعیت حساب قابل مشاهده است، اما ثبت‌نام با ایمیل و رمز هنوز جریان تأیید ایمیل ندارد و بلافاصله session صادر می‌کند. برای انطباق کامل با قانون موردنظر، یکی از این دو سیاست باید در مرحلهٔ بعد اعمال شود:

| سیاست | اثر | پیشنهاد |
|---|---|---|
| الزام تأیید تلفن در ثبت‌نام ایمیلی | ثبت‌نام ابتدا pending می‌شود و پس از OTP session کامل صادر می‌شود | مناسب وضعیت فعلی، چون SMS.ir آماده است. |
| ساخت email verification مستقل | ارسال لینک/کد از SMTP یا Resend و صدور session پس از تأیید | کامل‌تر، اما نیازمند فعال‌سازی و تست provider ایمیل است. |

تا قبل از اجرای یکی از این سیاست‌ها، `has_verified_factor=false` باید مانع عملیات حساس مانند انتشار مقاله، ایجاد پرداخت یا اقدامات مدیریتی شود؛ صرفاً داشتن password به‌تنهایی نباید عامل تأییدشده تلقی شود.

## تست production پس از تأیید قالب

پس از تأیید قالب و تنظیم secretها در Liara، این سناریوها باید اجرا شوند: ارسال به شمارهٔ معتبر با ارقام فارسی و انگلیسی؛ بررسی اینکه متن شامل لینک و پیشوند تستی پنل باشد؛ ورود کد صحیح؛ ورود کد اشتباه پنج بار؛ استفاده از کد پس از TTL؛ ارسال مجدد پیش از پایان ۶۰ ثانیه؛ ارسال مجدد پس از پایان تایمر؛ ورود با همان شماره در session جدید؛ افزودن شمارهٔ دوم از Dashboard؛ تلاش برای اتصال شماره‌ای که قبلاً به حساب دیگری متصل است؛ و بررسی `GET /auth/me` برای وجود `phone_verified=true` و `has_verified_factor=true`.

## وضعیت build

`npm run build` در frontend با موفقیت اجرا شد و `npm run check` در backend نیز بدون خطای TypeScript به پایان رسید. این بررسی‌ها جایگزین migration واقعی Liara یا تست ارسال واقعی SMS نیستند؛ migration شمارهٔ 016 باید یک‌بار روی database مقصد اجرا شود و سپس endpoint ارسال با template تأییدشده آزموده شود.
