## قابلیت‌های مرتبط با کاغذ و باد

SMS.ir برای اتصال برنامه‌نویسی‌شده، REST API و پکیج‌های Node.js، TypeScript، Python، PHP/Laravel، .NET و JavaScript ارائه می‌کند. برای backend فعلی Node.js/Fastify، استفاده از REST API یا پکیج Node.js مناسب‌تر از اتصال frontend است؛ کلید API و شمارهٔ خط نباید به bundle مرورگر منتقل شوند.

برای احراز هویت، سرویس Verify با endpoint رسمی `https://api.sms.ir/v1/send/verify` معرفی شده است. نمونهٔ رسمی از headerهای `Content-Type: application/json`، `Accept: text/plain` و `x-api-key` و بدنهٔ شامل `mobile`، `templateId` و `parameters` استفاده می‌کند. الگوی Verify باید در پنل ساخته شود و نام پارامترهای آن، مانند `Code`، باید دقیقاً با نامی که در درخواست API ارسال می‌شود یکسان باشد.

طبق مستندات رسمی، Verify برای پیامک‌های تأییدیه مانند ورود و ثبت‌نام مناسب است، مسیر ارسال اولویت بالاتری دارد، برای ارسال شبانه‌روزی معرفی شده و امکان ارسال به شماره‌هایی که دریافت پیامک تبلیغاتی را مسدود کرده‌اند دارد. فعال‌سازی واقعی همچنان به وضعیت پنل، اعتبار، خط و template تأییدشده وابسته است و باید با یک شمارهٔ آزمایشی واقعی در پنل بررسی شود.

## قابلیت‌های آینده‌نگر

علاوه بر Verify، مستندات و راهنمای SMS.ir قابلیت ارسال ساده و انبوه، ارسال زمان‌بندی‌شده و کمپین دوره‌ای/رویدادی، ارسال هوشمند با اطلاعات مخاطب، گزارش ارسال و دریافت، مدیریت مخاطبان و رویدادها، گزارش اعتبار و خطوط، ارسال به چند شماره و پکیج‌های آمادهٔ زبان‌های مختلف را نشان می‌دهد. صفحهٔ اصلی همچنین قابلیت‌هایی مانند پیامک سفید/باشگاه مشتریان، منشی پیامکی، گزارش ارسال و دریافت، و در برخی طرح‌ها ارسال منطقه‌ای را معرفی می‌کند. این قابلیت‌ها برای فازهای اطلاع‌رسانی مقاله، اعلان انتشار، دعوت Live، بازنشانی حساب، اعلان پرداخت و پنل مدیر قابل بررسی‌اند؛ برای هرکدام باید قوانین رضایت کاربر، محدودیت تبلیغاتی و هزینهٔ واقعی پنل جداگانه کنترل شود.

## مراحل موردنیاز داخل پنل

۱. تکمیل ثبت‌نام و احراز هویت پنل مطابق راهنمای SMS.ir؛ مستندات رسمی می‌گویند شمارهٔ ثبت‌نام باید به نام مالک پنل باشد و اطلاعات هویتی/نشانی برای فعال‌سازی بررسی می‌شود.

۲. انتخاب و فعال‌کردن پنل و شارژ اعتبار ارسال.

۳. ورود به بخش «برنامه‌نویسان» و ساخت API key.

۴. ایجاد یک الگوی Verify برای کاغذ و باد، مثلاً متن کوتاه شامل کد ورود و متغیر `Code`، سپس دریافت `templateId`.

۵. اطمینان از وجود خط خدماتی/OTP فعال برای Verify و یادداشت شمارهٔ خط فقط در صورت نیاز API یا گزارش‌ها.

۶. نگه‌داری API key در secret environment backend با نام پیشنهادی `SMSIR_API_KEY` و نگه‌داری `SMSIR_OTP_TEMPLATE_ID` به‌عنوان مقدار غیرمحرمانهٔ قابل تنظیم در backend؛ هیچ‌کدام نباید در frontend یا Git قرار گیرند.

## طرح امن اتصال به backend

frontend فقط endpoint داخلی کاغذ و باد را صدا می‌زند. backend شماره را normalize و اعتبارسنجی می‌کند، rate limit بر اساس IP/شماره اعمال می‌کند، کد را با TTL کوتاه و hash در PostgreSQL یا storage امن نگه می‌دارد، سپس فقط از backend به Verify API SMS.ir درخواست می‌فرستد. پاسخ API، request ID و نتیجهٔ ارسال بدون API key در audit ثبت می‌شود. کد خام نباید در log ذخیره شود.

برای جلوگیری از abuse، ارسال مجدد باید cooldown داشته باشد، تعداد تلاش verify محدود شود، پس از چند خطا کد منقضی شود، و برای شمارهٔ ایرانی canonicalization یکسان اجرا شود. در production باید یک مسیر health/config بدون افشای secret برای نمایش وضعیت پیکربندی (`configured`, `template_present`, `last_error_category`) به مدیر ارائه شود.

## وضعیت پنل در بررسی نشست فعلی

پس از ورود، داشبورد SMS.ir در دسترس بود. حساب دارای پلن رایگان و اعتبار نمایش‌داده‌شدهٔ ۱۵٬۳۴۰ ریال معادل ۵ پیامک بود. منوی «برنامه‌نویسان» شامل لیست کلیدهای API، لیست قالب‌ها، ارسال سریع، راهنمای API، آخرین خطاهای API و کتابخانه‌ها/افزونه‌هاست. همچنین بخش شماره‌های پیامکی، گزارش‌ها، تراکنش‌های مالی، مخاطبان، منشی پیامکی و هم‌تیمی‌ها فعال و قابل مشاهده بود.

صفحهٔ `/developer/list` هنگام بررسی در حالت بارگذاری باقی ماند و هنوز وجود یا نبود کلید API از طریق UI تأیید نشده است. تا این مرحله هیچ کلید، قالب یا تنظیمی ایجاد یا تغییر داده نشده است. اعتبار فعلی برای تست‌های محدود OTP ممکن است کافی باشد، اما وضعیت template و فعال‌بودن Verify باید در پنل تأیید شود.

## نتیجهٔ بررسی API و قالب‌ها

در فهرست کلیدهای API دو کلید فعال از نوع «عملیاتی - Production» وجود دارد؛ یکی با عنوان «احراز» و دیگری با عنوان «Xtrimer». کلیدها فقط به‌صورت ماسک‌شده نمایش داده شدند و هیچ secret از پنل استخراج یا در گزارش ثبت نشد. وجود کلید «احراز» نشان می‌دهد دسترسی برنامه‌نویسی برای مسیر احراز قبلاً آماده شده است، اما مقدار کلید باید از طریق گزینهٔ مشاهده و سپس به‌صورت امن در secret محیط backend قرار گیرد.

در صفحهٔ «قالب‌های ارسال سریع» هیچ قالب فعالی نمایش داده نشد و وضعیت صفحه «اطلاعاتی جهت نمایش یافت نشد» بود. بنابراین برای Verify API هنوز باید یک قالب OTP در پنل ایجاد و پس از تأیید، template ID آن ثبت شود. تا ایجاد قالب، هیچ ارسال واقعی از backend انجام نمی‌دهم.

## قالب OTP ثبت‌شده

قالب `KaghazBaad Login OTP` با دستهٔ OTP و متغیر سیستمی `#CODE#` با موفقیت در پنل ذخیره شد. شناسهٔ قالب `888623` است و وضعیت فعلی آن «در حال بررسی» نمایش داده می‌شود. تا زمان تأیید SMS.ir، درخواست واقعی Verify را از backend فعال نمی‌کنم؛ پس از تأیید می‌توان همین template ID را در `SMSIR_OTP_TEMPLATE_ID` قرار داد.

## وضعیت اجرای اتصال در کاغذ و باد

Adapter موجود backend از قبل با endpoint رسمی Verify یعنی `https://api.sms.ir/v1/send/verify` سازگار بود و از `x-api-key`، `mobile`، `templateId` و `parameters` استفاده می‌کند. در Liara، `SMSIR_API_KEY` از کلید فعال با عنوان «احراز» و `SMSIR_TEMPLATE_ID=888623` به‌صورت secret/environment backend تنظیم شد؛ مقدار کلید در log یا گزارش ثبت نشده است. `SMSIR_CODE_PARAMETER=Code` نیز صریحاً تنظیم شد تا با قرارداد نمونهٔ رسمی API و adapter فعلی هماهنگ باشد.

پس از restart، `https://api.kaghazobaad.ir/api/v1/health` با HTTP 200 پاسخ داد. endpoint مدیریتی تنظیمات Auth بدون session با HTTP 401 پاسخ داد که نشان می‌دهد کنترل دسترسی برقرار است. ارسال واقعی OTP هنوز اجرا نشده، زیرا قالب `888623` در پنل SMS.ir در وضعیت «در حال بررسی» است. بعد از تأیید قالب، باید یک تست کنترل‌شده با شمارهٔ واقعی کاربر انجام شود؛ آن تست یک پیامک مصرف می‌کند و تا آن زمان سیستم باید وضعیت provider-not-ready را به‌صورت امن گزارش کند.

## نتیجهٔ بررسی مستندات دربارهٔ لینک سایت
