# پیشنهاد UI و UX برای «کاغذ و باد»

**دامنهٔ بررسی:** سایت عمومی، صفحهٔ خانه، navigation، آرشیو مقالات و مسیرهای دوزبانه.  
**تاریخ بررسی:** ۲۰ اوت ۲۰۲۶  
**روش:** بازدید از سایت زنده، بررسی مسیر `/read`، مطالعهٔ ساختار route و componentهای ریپوی پروژه، و مقایسه با منابع مرجع تعاملات وب.

## خلاصهٔ مدیریتی

«کاغذ و باد» از نظر هویت بصری یک نقطهٔ شروع متمایز دارد: پس‌زمینهٔ سرمه‌ای، تصویر مغز صورتی و ایدهٔ نشر آکادمیک دوزبانه، همگی امکان ساختن یک تجربهٔ آرام و به‌یادماندنی را فراهم می‌کنند. بااین‌حال، در وضعیت فعلی صفحهٔ خانه بیشتر شبیه یک **ورودی جست‌وجو** است تا یک landing page که ارزش محصول، مخاطب و اقدام بعدی را توضیح دهد. در بازدید زنده، محتوای اصلی پس از shell اولیه با تأخیر دیده شد و صفحهٔ مقالات نیز بعد از loading به empty state بسیار خلوت رسید.

پیشنهاد اصلی من این است که پروژه در فاز نخست به‌جای افزودن WebGL یا motion سنگین، روی سه چیز تمرکز کند: **شفاف‌کردن روایت و CTA در خانه، تبدیل آرشیو به تجربهٔ کشف محتوا، و ساختن یک سیستم تعامل قابل‌دسترس که بدون animation نیز کامل باشد.** سپس می‌توان از استعارهٔ کاغذ، باد و ورق‌زدن برای غنی‌سازی تدریجی استفاده کرد.

> معیار تصمیم‌گیری: هر جلوهٔ بصری باید یا به فهم محتوا، جهت‌یابی، بازخورد وضعیت یا هویت محصول کمک کند؛ در غیر این صورت هزینهٔ عملکرد و پیچیدگی آن توجیه ندارد.

## بازطراحی پیشنهادی صفحهٔ خانه

### ساختار محتوایی

خانه بهتر است از یک صفحهٔ صرفاً تعاملی به روایت کوتاه و قابل‌اسکن تبدیل شود. در اولین viewport، لوگو/تصویر مغز حفظ شود، اما در کنار آن یک تیتر روشن، یک توضیح یک‌جمله‌ای و دو اقدام مشخص قرار گیرد. نمونهٔ پیشنهادی برای فارسی چنین است:

> **دانش را بنویس، به اشتراک بگذار و دوباره به گفت‌وگو برگردان.**  
> کاغذ و باد، فضای نشر آکادمیک دوزبانه برای مقاله، اسلاید و گفت‌وگوی زنده است.

CTA اصلی می‌تواند «مشاهدهٔ مقالات» و CTA ثانویه «آشنایی با پروژه» باشد. جست‌وجو همچنان باید در مرکز تجربه بماند، اما زیر یک label یا heading واضح مانند «در مقالات جست‌وجو کنید» قرار گیرد تا نقش آن برای کاربر روشن باشد.

پس از hero، سه کارت کوتاه برای «مقاله»، «نمایش اسلایدی» و «پخش زنده» اضافه شود. این کارت‌ها نباید صرفاً decorative باشند؛ هرکدام باید یک خروجی واقعی و یک لینک مشخص داشته باشد. بخش پایانی خانه نیز می‌تواند یک نمونهٔ مقالهٔ منتخب، یک توضیح کوتاه دربارهٔ استاندارد انتشار، و CTA دعوت/ورود را نشان دهد.

### سلسله‌مراتب دیداری

تصویر مغز بهتر است به‌عنوان **نشانهٔ هویتی و همراه تیتر** عمل کند، نه تنها پیام صفحه. اندازهٔ آن در موبایل باید کاهش یابد و در حالت reduced motion ثابت بماند. اگر animation فعلی چشمک‌زن یا loop دارد، باید برای آن نسخهٔ ثابت، `aria-hidden` مناسب برای بخش تزئینی و متن جایگزین در سطح محتوایی در نظر گرفته شود.

## navigation و معماری اطلاعات

در دسکتاپ، پیشنهاد می‌شود «مقالات» و «پخش زنده» به‌عنوان دو مسیر اصلی مستقیماً در هدر باقی بمانند. «درباره» می‌تواند یک منوی ثانویه باشد، اما «شرح پروژه» نباید در عمق منو پنهان شود؛ این صفحه برای اعتمادسازی و فهم محصول مهم است. آیکون جست‌وجو نیز بهتر است در کنار عنوان یا به‌صورت یک دکمهٔ دارای label «جست‌وجوی مقاله» نمایش داده شود، نه فقط یک آیکون بدون متن.

در موبایل، منوی تمام‌صفحه یا sheet فعلی باید یک ترتیب ساده داشته باشد: خانه، مقالات، پخش زنده، دربارهٔ پروژه، دربارهٔ ما، زبان و تم. منو باید با `Escape` بسته شود، focus را هنگام بازشدن داخل خود نگه دارد و پس از بسته‌شدن focus را به دکمهٔ منو برگرداند. labelهای فارسی و انگلیسی باید از نظر طول و شکست خط جداگانه بررسی شوند.

## جست‌وجو: مسیر پیشنهادی کامل

پیاده‌سازی فعلی از نظر debounce، پیشنهادهای API، انتخاب با کلیدهای بالا/پایین و submit پایهٔ مناسبی دارد. برای تبدیل آن به تجربهٔ production-ready، این قرارداد پیشنهادی را اعمال کنید:

| وضعیت | رفتار پیشنهادی |
|---|---|
| قبل از ورود متن | placeholder، label قابل‌خواندن برای screen reader و hint کوتاه دربارهٔ نوع جست‌وجو |
| متن کمتر از دو نویسه | عدم فراخوانی API و نمایش پیام خنثی؛ نه خطا |
| loading | spinner یا progress کوچک همراه با `aria-busy` روی listbox |
| پیشنهادها | استفاده از الگوی combobox/listbox، `aria-activedescendant` و announcement انتخاب |
| بدون نتیجه | نمایش «نتیجه‌ای پیدا نشد» به‌همراه لینک «مشاهدهٔ همهٔ مقالات» و پیشنهاد اصلاح عبارت |
| خطای API یا rate limit | پیام inline نزدیک جست‌وجو با امکان تلاش دوباره؛ toast نباید تنها کانال خطا باشد |
| submit | انتقال به URL قابل اشتراک مانند `/read?q=...` و حفظ query در input |

## آرشیو مقالات و empty state

صفحهٔ `/read` باید از سه حالت «جدیدترین»، «موضوعات» و «جست‌وجو» پشتیبانی کند. هر کارت مقاله بهتر است عنوان فارسی/انگلیسی، نویسنده یا نهاد، تاریخ/نسخه، زمان تقریبی مطالعه، وضعیت انتشار و یک preview تصویری یا اولین اسلاید را نشان دهد. کارت باید دو اقدام داشته باشد: «خواندن مقاله» و «مشاهدهٔ اسلایدها»؛ این تفکیک با وعدهٔ فعلی «نمایش اسلایدی» هم‌راستا است.

در حالت بدون مقاله، به‌جای یک جملهٔ تنها، یک empty state کاربردی بسازید: توضیح اینکه آرشیو هنوز در حال شکل‌گیری است، CTA «بازگشت به خانه»، CTA «دربارهٔ پروژه» و در صورت وجود حساب، گزینهٔ «اطلاع از انتشار مقالهٔ جدید». loading، خطای شبکه و نبود داده باید از نظر متن و visual از هم متمایز باشند.

## پیشنهاد برای نمایش مقاله و page-turn

منبع Complete Shelf نشان می‌دهد که یک تجربهٔ bookshelf می‌تواند چند مسیر ورودی داشته باشد: wheel، کلیدهای جهت، دکمه، position marker و interaction مستقیم؛ همچنین کنترل‌های HTML و status announcement باید روی صحنهٔ تعاملی قرار بگیرند.[1] این الگو برای کاغذ و باد ارزشمند است، اما بهتر است به‌صورت سبک و progressive enhancement بازنویسی شود.

برای نسخهٔ اول، نمایش مقاله را دوحالته طراحی کنید. حالت پیش‌فرض باید خواندن سریع با scroll و HTML semantic باشد. حالت «نمایش اسلایدی» می‌تواند page-turn نرم داشته باشد، اما همیشه دکمه‌های قبلی/بعدی، شمارهٔ صفحه، progress، کلیدهای ArrowLeft/ArrowRight، swipe و لینک «بازگشت به متن کامل» فعال بمانند. در RTL، معنای قبلی/بعدی باید از نظر ترتیب محتوا روشن و مستقل از جهت فیزیکی animation تعریف شود.

الگوی state machine پیشنهادی چنین است: `archive → preview → reading → slides → references → discussion`. state نمایشی مانند slide index و drag offset باید محلی و موقت بماند؛ وضعیت واقعی انتشار، تأیید و جلسهٔ زنده باید از backend بیاید.

## motion، texture و زبان بصری

برای هویت «کاغذ و باد»، یک texture بسیار ظریف کاغذی، reveal مرحله‌ای هنگام ورود sectionها و حرکت محدود لایه‌های hero کافی است. از pointer parallax منبع Sylva فقط به‌عنوان الگو استفاده کنید؛ خود WebGL تمام‌صفحه برای خانه ضروری نیست. صفحهٔ عمومی باید بدون WebGL و حتی با JavaScript محدود، HTML خوانا و CTAهای قابل استفاده داشته باشد.[2]

ذرات کاغذ یا باد فقط وقتی ارزش دارند که فصل‌بندی یا جهت حرکت را توضیح دهند. روی موبایل ضعیف و در `prefers-reduced-motion: reduce` خاموش شوند. scroll hijacking، cursor trail دائمی، blur زیاد و audio خودکار پیشنهاد نمی‌شوند؛ این عناصر به‌راحتی تمرکز، خوانایی و عملکرد را تضعیف می‌کنند.

## دسترس‌پذیری و responsive

هر دکمهٔ icon-only باید label واقعی داشته باشد و focus ring آن روی پس‌زمینهٔ تیره و روشن واضح باشد. متن placeholder نباید جای label را بگیرد. برای فرم جست‌وجو، focus، خطا و نتیجه باید با متن و نه فقط رنگ منتقل شود. مسیرهای اصلی باید با keyboard کامل قابل استفاده باشند و با screen reader نام و وضعیت کنترل‌ها را اعلام کنند.

در responsive design، breakpointها را بر اساس شکست واقعی navigation و کارت‌ها انتخاب کنید، نه فقط اندازه‌های متداول دستگاه. در عرض کم، hero باید اول تیتر و CTA را قابل مشاهده کند و تصویر هویتی بعد از آن بیاید. در صفحهٔ مقاله، ستون متن نباید بیش از حد عریض شود؛ عرض خواندن محدود، line-height مناسب فارسی و فاصلهٔ کافی بین پاراگراف‌ها اهمیت بیشتری از تزئینات دارد.

## performance و SEO

ریسک مشاهده‌شدهٔ blank/late content باید با اندازه‌گیری LCP، CLS و INP در desktop و mobile بررسی شود. برای کنترل آن، تصویر مغز را با ابعاد صریح و فرمت بهینه عرضه کنید، animation را پس از محتوای اصلی فعال کنید، routeهای سنگین مانند deck و live را lazy-load نگه دارید و از hydration/loader طولانی برای shell عمومی جلوگیری کنید. متن تیتر، توضیح محصول و کارت‌های مقاله باید در HTML قابل ایندکس باقی بماند.

در هر route عمومی، title، description، canonical، Open Graph و structured data باید با زبان همان route تولید شود. تغییرات visual نباید متن قابل‌خزش را به canvas یا WebGL منتقل کند. این موضوع با معماری فعلی routeهای public SEO هم‌راستاست و باید در preview و build نهایی دوباره verify شود.

## جمع‌بندی تصمیم‌های اجرایی

برای این پروژه، بهترین مسیر **progressive enhancement** است: ابتدا تجربهٔ کامل و سریع با HTML، CSS و React؛ سپس motion سبک؛ و تنها در صورت اثبات ارزش محصول، viewer یا scene تعاملی. از منابع مرجع، state machine، کنترل‌های چندگانه، position marker و لایهٔ HTML دسترس‌پذیر را اقتباس کنید؛ اما صحنه‌های سنگین Three.js، audio و assetهای منبع را بدون بررسی مجوز، نیاز واقعی و budget عملکرد وارد production نکنید.

سه اقدام پیشنهادی برای شروع عبارت‌اند از: اول، بازنویسی hero با روایت و CTA؛ دوم، اصلاح جست‌وجو و empty state؛ و سوم، تعریف design token و checklist تست برای RTL، keyboard، reduced motion، mobile و SEO. این سه اقدام بیشترین اثر را بر فهم محصول و completion مسیر کاربر دارند و پیش‌نیاز امنی برای page-turn و motion آینده هستند.
